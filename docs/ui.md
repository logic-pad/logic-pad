# Logic Pad — UI Guide

This document covers the frontend (`src/client`): tech stack, structure,
design language, key concepts, and how to verify UI changes visually.

## Tech stack

- **React 19 + Vite** SPA, **TanStack Router** (file-based routes) and
  **TanStack Query** for data fetching
- **jotai** (+ `jotai-scope`) for state management
- **Tailwind CSS v4 + DaisyUI v5** for styling; all bundled DaisyUI themes are
  supported and color-tweaked in `src/client/index.css`
- **Monaco editor** for the puzzle source code editor
- **Bun** as package manager / script runner (Node also works for most things)

## Repository structure

```
src/
  client/                  All frontend code
    routes/                TanStack Router file-based routes
    router/routeTree.gen.ts  GENERATED by the router plugin — never edit
    screens/               Full-screen layouts (see "Screens" below)
    editor/                Puzzle editor components (tabs, toolbox, checklist)
    online/                API client + online UI (comments, collections, cards)
    components/            Shared UI components
    metadata/              Puzzle metadata display (title, difficulty, author)
    instructions/          Instruction (rule/symbol) list, search, and "parts"
    grid/                  Grid rendering (canvas/DOM), overlays, mouse handling
    state/                 jotai atoms + state scopes (scopes/ subfolder)
    index.css              Tailwind/DaisyUI setup + per-theme color tweaks
  ssr/                     Elysia production server (SSR meta tags, static hosting)
packages/
  logic-core/              All puzzle logic (@logic-pad/core): grid data model,
                           rules, symbols, serializers, validators, solvers
```

The backend is a **separate project** (`logic-pad-api`). In dev, Vite proxies
`/api/*` to `http://localhost:3000` (see `vite.config.ts`). Frontend and
backend versions are checked at runtime; a version mismatch toast is normal
when the backend is older.

## Key concepts

### Generic vs puzzle-specific UI

The design language is built around the assumption that the site could host
many puzzle types (even though only 2D grid coloring puzzles exist today):

- **Generic UI** (nav bars, metadata, comments, collections, all non-puzzle
  pages) uses **base colors** (`bg-base-100/200`, `text-base-content`).
- **Puzzle-specific UI** (the grid, instruction list, puzzle controls) lives
  inside a **`PuzzleSurface`** (`src/client/components/PuzzleSurface.tsx`): a
  raised, rounded, shadowed **neutral-colored** panel. Neutral guarantees
  contrast for black/white tiles in every theme.

Never put puzzle grids on base colors, and don't style generic chrome with
neutral colors.

### Screens and layout

- `screens/PuzzlePlayScreen.tsx` — shared solve layout used by both
  `SolveScreen` and `PerfectionScreen`: generic left sidebar + puzzle surface
  (grid area + right instruction sidebar). Comments and collection lists open
  as panels inside the left sidebar via `SolveScreenContext`, keeping the grid
  interactive. On narrow screens the sidebar collapses into a top bar that
  expands to a full-screen overlay.
- `screens/PuzzleEditorScreen.tsx` — editor with a screen-width top bar
  (`editor/EditorTopBar.tsx`: puzzle info + `PuzzleSaveControl` + tabs) and
  three full-screen tabs:
  - **Info** (`editor/EditorInfoTab.tsx`) — generic: metadata editor,
    non-collapsible checklist, online stats/publishing, comments. Responsive
    3/2/1-column grid.
  - **Edit** (`editor/EditorEditTab.tsx`) — puzzle-specific: toolbox
    (collapsible to a single vertical column of buttons, collapsed by default
    below 1280px), grid, instruction list, preview button, collapsible
    checklist.
  - **Code** (`editor/SourceCodeEditor.tsx`) — Monaco editor + quick
    reference + "Load puzzle" button.
- `components/GridControlsBar.tsx` — combined edit/touch controls (undo,
  redo, reset, validator status, flood fill, zoom slider, B/W primary-color
  swap) as one floating bar, horizontally **centered to the grid area** (not
  the whole puzzle surface). Narrow screens get the two-row stacked design
  with a large color switch.

### Responsiveness: prefer CSS over JS media queries

Layout breakpoints are done with Tailwind responsive classes on a **single
component tree**. Do not use `useMediaQuery` to switch between different
component trees for layout — it breaks headless rendering, causes mount
flips, and can double-fire effects (e.g. hotkeys). If interactive elements
appear in two visual variants, mount them once and restyle with CSS, or lift
their state up and render two pure presentational variants.

### State management and scopes

Global state lives in jotai atoms under `src/client/state/`. Stateful screens
wrap their content in **scopes** (`state/scopes/`) using `jotai-scope`, so
multiple puzzle instances (main page + embedded modals) never share atoms:

- `PuzzleScope` — the loaded puzzle (grid, metadata, solution, online info)
- `EditorScope` — toolbox and config popup state
- `EmbedScope` — marks an embedded instance and toggles **embed features**
  (`embedFeaturesAtom`: `instructions`, `metadata`, `checklist`, `saveControl`,
  `preview`). Respect these flags when adding editor/solve UI.
- `EmbeddedPuzzleScope` — a `PuzzleScope` for embedded puzzles

### Instruction parts

Rules and symbols can contribute extra UI at placements defined in
`instructions/parts/types.ts` (`LeftPanel`, `LeftBottom`, `MainGridOverlay`,
`GridOverlay`, `Toolbox`). They render through `InstructionPartOutlet` at the
appropriate location: overlays on the grid, toolbox parts in the editor
toolbox, and panel parts in the right sidebar of the puzzle surface (below
the instruction list).

### Modes and grids

A puzzle has modes (`create`, `solve`, `perfection`). `ModeVariantLoader`
transforms rules/symbols for the active mode. Grid data comes from
`@logic-pad/core` (`GridData`, `Rule`, `Symbol`); puzzles serialize through
`Serializer`/`Compressor` into the `?d=` URL parameter for offline links.

### Generated files

- `src/client/router/routeTree.gen.ts` is regenerated by the router Vite
  plugin on every file change.
- After modifying `packages/logic-core`, run `bun build` inside it to
  regenerate its assets.

## Common commands

```bash
bun run dev          # Vite dev server on :5173 (proxies /api to :3000)
bun run lint         # eslint (also runs prettier checks)
bunx --bun tsc --noEmit   # type check
bun run build        # tsc + production build into dist/
```

Always run lint + tsc before considering a change done.

## Visual debugging

A headless Chrome + CDP (Chrome DevTools Protocol) workflow lets you verify
UI without a display. Chrome headless alone cannot reliably wait for SPA
rendering or click elements, so drive it with a small Node script (Node 22+
has a built-in WebSocket client; on Node 20 run it with
`--experimental-websocket`):

```js
// shot.mjs — cross-platform CDP screenshot tool
// Usage: node shot.mjs <url> <out.png> [width] [height] [waitMs] [initScriptFile] [postScriptFile]
import { spawn } from 'node:child_process';
import { writeFileSync, readFileSync, rmSync, mkdtempSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

const [, , url, out, W = '1600', H = '900', WAIT = '6000', initFile, postFile] =
  process.argv;
const CHROME =
  process.env.CHROME_PATH ??
  (process.platform === 'win32'
    ? 'C:/Program Files/Google/Chrome/Application/chrome.exe'
    : process.platform === 'darwin'
      ? '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome'
      : 'google-chrome');
const PORT = 9223;
const profile = mkdtempSync(join(tmpdir(), 'shot-'));
const chrome = spawn(
  CHROME,
  [
    '--headless=new',
    '--disable-gpu',
    `--remote-debugging-port=${PORT}`,
    `--user-data-dir=${profile}`,
    `--window-size=${W},${H}`,
    '--hide-scrollbars',
    'about:blank',
  ],
  { stdio: 'ignore' }
);
const sleep = ms => new Promise(r => setTimeout(r, ms));
const wsUrl = await (async () => {
  for (let i = 0; i < 50; i++) {
    try {
      const list = await (
        await fetch(`http://127.0.0.1:${PORT}/json/list`)
      ).json();
      const page = list.find(t => t.type === 'page');
      if (page) return page.webSocketDebuggerUrl;
    } catch {}
    await sleep(200);
  }
  throw new Error('devtools not reachable');
})();
const ws = new WebSocket(wsUrl);
await new Promise((res, rej) => ((ws.onopen = res), (ws.onerror = rej)));
let id = 0;
const pending = new Map();
ws.onmessage = e => {
  const m = JSON.parse(e.data);
  if (m.id && pending.has(m.id)) {
    m.error ? pending.get(m.id)[1](new Error(m.error.message)) : pending.get(m.id)[0](m.result);
    pending.delete(m.id);
  }
};
const send = (method, params = {}) =>
  new Promise((res, rej) => pending.set(++id, [res, rej]) && ws.send(JSON.stringify({ id, method, params })));
await send('Page.enable');
await send('Emulation.setDeviceMetricsOverride', {
  width: +W, height: +H, deviceScaleFactor: 1, mobile: +W < 768,
});
if (initFile)
  await send('Page.addScriptToEvaluateOnNewDocument', {
    source: readFileSync(initFile, 'utf8'),
  });
await send('Page.navigate', { url });
await sleep(+WAIT);
if (postFile) {
  const r = await send('Runtime.evaluate', {
    expression: readFileSync(postFile, 'utf8'),
    awaitPromise: true,
    returnByValue: true,
  });
  console.log('postScript:', JSON.stringify(r.result?.value ?? r.exceptionDetails?.text));
}
const shot = await send('Page.captureScreenshot', { format: 'png' });
writeFileSync(out, Buffer.from(shot.data, 'base64'));
chrome.kill();
await sleep(1000);
rmSync(profile, { recursive: true, force: true });
```

Typical usage:

- Screenshot a page: `node shot.mjs http://localhost:5173/ home.png`
- Mobile layout: pass `480 900` as width/height.
- Click before shooting (e.g. open the editor Info tab) with a post-script:

  ```js
  // post.js
  (async () => {
    [...document.querySelectorAll('[role=tab]')]
      .find(t => t.textContent === 'Info')
      ?.click();
    await new Promise(r => setTimeout(r, 1500));
    return 'done';
  })();
  ```

- Control site state via an init script (runs before page scripts). Two
  localStorage keys matter:
  - `theme` — JSON string of a DaisyUI theme name, e.g.
    `localStorage.setItem('theme', JSON.stringify('light'))`
  - `siteSettings` — JSON object; e.g. disable the editor tour with
    `localStorage.setItem('siteSettings', JSON.stringify({runEditorTour:false}))`

### Gotchas

- **Stale Vite modules after deleting/renaming files**: the dev server keeps
  serving old transformed modules under `?t=<timestamp>` URLs, causing
  "Failed to fetch dynamically imported module" errors. Restart the dev
  server (kill the process listening on port 5173 — on Windows it's a `node`
  process, not `bun`).
- **OAuth sign-in cannot be automated.** For signed-in-only screens (comment
  posting, online saves, `/settings`), verify by code review and ask the user
  for screenshots.
- **Backend must run for online features**: `/api` returns 500s and the site
  shows "Offline" otherwise. The backend is a separate project
  (`logic-pad-api`, `bun run dev`, port 3000).
- **`useMediaQuery` is unreliable in headless** (initializes false) — another
  reason to keep layout responsive in CSS only.
- **Monaco inside indefinite-height flex chains collapses to ~5px**:
  `height: 100%` can't resolve against flex-grown heights when the page
  height is content-driven (mobile). Give the editor container an explicit
  height (`h-[60vh]` on mobile) and keep `automaticLayout: true` in Monaco
  options.
- `useSettings` values are validated by zod with `catch`, so partial
  `siteSettings` JSON is fine (missing keys get defaults).

### Useful test data

The dev backend (when running) contains public puzzles and collections. Query
`GET /api/puzzle/search` and `GET /api/collection/search` via the Vite proxy
(`http://localhost:5173/api/...`) to find IDs, then visit
`/solve/<id>`, `/solve/<id>?collection=<collectionId>`,
`/perfection/<id>`, `/create`, `/create/<id>`.
